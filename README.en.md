# Glane

Sensor layer and device publishing for **QNX 8.0**.

Candidate project for the **QNX Global Hackathon**, category **Low-level Software**.
Submission deadline: **15 December 2026, 20:00 (Europe/Paris)**.

- **Live demo (virtual publisher in the browser):** <https://tradoooo.github.io/glane/>
- **Live QNX 8.0 guest (VGA screen + serial console):** <https://baptiste-ms-7d18.tail3a8bdf.ts.net:10000>
- **Repository:** <https://github.com/Tradoooo/glane>

> **What is real and what is virtual.** The operating system in every recording
> of this repository is a **real QNX 8.0.0** (a real `procnto-smp-instr`, a real
> `ksh`, real resource managers) booted as a guest under QEMU. The **sensors are
> virtual**: they are synthetic waveforms produced by the Glane virtual publisher.
> No Raspberry Pi 5 and no physical sensor is involved in anything recorded
> here. Nothing in this README claims otherwise.

## The idea in one sentence

A sensor — real on a Raspberry Pi 5, or simulated under QEMU — is described in
a file, discovered, calibrated, published into the system namespace with
**source timestamping**, and its publication latency is **measured and bounded**,
without hand-writing a resource manager. *Of the two cases above, only the
second one exists in this repository: every run recorded here is a simulated
sensor inside a real QNX 8.0 guest.*

## What QNX ships today, and the gap

QNX ships a device-publishing framework and **one** publisher (`usblauncher_otg`,
oriented toward USB / storage / media). Nothing for sensors, no documented API
for authoring a publisher, no simulation without hardware, no conformance
validator, no latency measurement. Glane does not reinvent the mechanism: it
supplies the five missing pieces so the mechanism can actually be used.

| # | Gap in what QNX ships (sourced in the QNX Device Publishers guide) | What Glane adds |
|---|---|---|
| 1 | One publisher only (`usblauncher_otg`, USB/storage/media); nothing for sensors | `core/` — a portable, pure-C11 library to describe, validate and calibrate a sensor, plus the ring buffer, the staleness/fault rules and the published-object schema |
| 2 | No documented API or SDK for writing a publisher (`dev_pub/about.html`) | A frozen contract (`CONTRACT.md`) + reference QNX publishers (`target/glaned.c`, `publish/qnx/`) |
| 3 | No simulation or hardware-free test anywhere in the guide | The virtual publisher (`build/glaned-sim`, `glaned` on QNX): deterministic synthetic measurements, replayable byte for byte |
| 4 | No conformance validator for the published object tree, although the tree is imposed (`dev_pub/rmps_objects.html`) | `host/gschema.py` — validates a real published tree, non-zero exit on any deviation (GLA-08) |
| 5 | Nothing about publication latency, notification timestamping or QoS (`dev_pub/rmps_objects.html`) | `host/glat.py` — the latency bench (p50 / p99 / p99.9 / max) and `host/greport.py` — the standalone HTML report (GLA-09) |

## Portable core

Strict C11, pure (no clock, no file, no socket, no `malloc`, no global state),
compiles and tests on Linux with `gcc -std=c11 -O2 -Wall -Wextra -Werror`.

```
core/
├── include/glane/   glane_sample.h glane_calib.h glane_desc.h glane_bus.h
│                    glane_ring.h glane_deadline.h glane_schema.h
│                    glane_virtuel.h glane_saturate.h glane_selftest.h
│                    glane_jsonscan.h
├── src/             sample.c calib.c ring.c deadline.c schema.c
│                    desc.c desc_validate.c jsonscan.c
│                    virtuel.c saturate.c selftest.c
└── tests/           test_*.c + test_util.h + faulty/ (40 cases) + valid/
```

Everything that touches the operating system is isolated in `publish/qnx/` and
`target/`, and is never compiled by the host Makefile: `target/glaned.c` guards
its QNX-specific code with `#ifdef __QNX__` and keeps a portable stdout
fallback, and `publish/qnx/glane_publish.c` is only built by `qnx/build.sh`
with `qcc`. `image/` holds the QNX buildfile templates (`mkifs`).

## Tools

| Tool | Language | Role |
|---|---|---|
| `build/glaned-sim` | C (host) | virtual publisher: description → deterministic synthetic measurements → journal |
| `build/calib_dump` | C (host) | dump of `glane_calib_apply` for the C↔Python differential test |
| `host/gschema.py` | Python | conformance validator of the published tree (GLA-08) |
| `host/glat.py` | Python | latency bench, p50 / p99 / p99.9, from a journal (GLA-09) |
| `host/greport.py` | Python | standalone HTML report of a measurement campaign |
| `host/gcanon.py` | Python | JSON canonicalisation + stable SHA-256 fingerprint |
| `host/glane_twin.py` | Python | twin of the integer calibration (differential test, GLA-05) |
| `scripts/glane_mutate.py` | Python | mutation test of the C core (≥ 8 mutants, all killed) |
| `scripts/glane_trace.py` | Python | GLA-01..24 traceability matrix |
| `scripts/sizecheck.py` | Python | size guard (< 500 lines/file, < 50 lines/function) |

QNX-side binaries (built with `qcc`, not by the host Makefile):

| Binary | Role |
|---|---|
| `target/glaned.c` | the publisher: publishes the sensors into the guest namespace |
| `publish/qnx/glane_publish.c` | publication layer: publication root, six leaves per sensor |
| `target/gwatch.c` | subscriber: re-reads a published value and raises an alarm above a threshold |
| `target/gsensor_resmgr.c` | QNX resource manager exposing `/dev/sensors/<name>` |
| `target/gsuper.c` | supervisor: restarts the publisher when it dies (HAM-style) |
| `tools/qnxproof.c` | prints the guest's own `uname` identity (proof of execution) |

## Build and test

```sh
make            # static library + test binaries + host tools
make test       # C tests — each binary ends with "OK <n> checks"
make host-test  # host Python tests (unittest): twin, differential, gschema, glat, greport, gcanon, trace
make asan       # C tests under AddressSanitizer + UndefinedBehaviorSanitizer
make sizecheck  # size guard
make fuzz       # deterministic parser fuzz, 100 000 inputs, under ASan/UBSan
python3 scripts/glane_mutate.py   # mutation test (every mutant must be killed)
python3 scripts/glane_trace.py     # traceability matrix (Markdown)
```

### Express demo (virtual publisher → latency → report)

```sh
make all
./build/glaned-sim core/tests/valid/temp-chassis.json 2000 sine 42 1500000 /tmp/j.jsonl
python3 host/glat.py /tmp/j.jsonl                 # p50 / p99 / p99.9 latency
python3 host/greport.py /tmp/j.jsonl /tmp/report.html
```

Two runs of `glaned-sim` with the same parameters produce the same journal
**byte for byte** (deterministic replay, GLA-04) — verified here:
`cmp /tmp/j1.jsonl /tmp/j2.jsonl` → identical, same SHA-256.

## Running on QNX 8.0

### Toolchain and build

- **SDP 8.0** (QNX Software Center), `qcc` **12.2.0**, target variant
  `gcc_ntox86_64` (x86_64) — recorded in `qnx/capture/build-proof.txt` and
  `qnx/capture/runtime-howto.md`.
- Build:

  ```sh
  bash qnx/build.sh          # -> build-qnx/glaned
  ```

  Result recorded in `qnx/capture/build-proof.txt`: exit `0`, **no warning**
  under `-Wall -Wextra`, 32 976-byte ELF 64-bit x86-64 binary, dynamic,
  interpreter `/usr/lib/ldqnx-64.so.2`. The pure `core/` sources compile
  unmodified with `qcc`.
- Full run (compile → build the IFS → boot → capture):

  ```sh
  bash qnx/run-glane-qemu.sh
  ```

### The guest image

A minimal QNX IFS assembled by `qnx/glane-ifs.build` with `mkifs`
(`[image=24m]`): `procnto-smp-instr` + `startup-x86` (serial console at
115200) + `glaned` + `qnxproof` + `ksh` + `toybox` + `pidin`. It has **no disk
and no network**. Its size is measured, not hard-coded: the capture script
writes the real size of the built image into `qnx/capture/runtime-howto.md`
(the image in the build tree, `build-qnx/glane-ifs.bin`, is ~5.7 MiB).

It is booted with `-kernel` (no disk image) and `-cpu max`:

```sh
qemu-system-x86_64 -kernel build-qnx/glane-ifs.bin -m 512 -smp 1 -cpu max \
  -display none -vga none -serial file:build-qnx/qnx-console.log -no-reboot
```

### Proof that a real OS ran inside the guest

`qnxproof` calls `uname(2)` **inside the guest** and prints the result. From
`qnx/capture/runtime-uname.txt`:

```
[QNX-PROOF] sysname=QNX release=8.0.0 version=2026/06/05-16:26:03EDT machine=x86pc node=localhost
```

and `uname -a` from the same console (`qnx/capture/runtime-console.txt`):

```
QNX localhost 8.0.0 2026/06/05-16:26:03EDT x86pc x86_64
```

### What the guest actually shows

Every line below is in `qnx/capture/runtime-console.txt` (and, for the
publication part, in `qnx/capture/runtime-glaned.txt`).

| What | Evidence in the capture |
|---|---|
| The QNX process table | the guest runs `pidin` (`qnx/glane-ifs.build`, line 32: `pidin -F "%n %a"`) → `/proc/boot/procnto-smp-instr` (pid 1), `proc/boot/pidin` |
| **3 sensors published at 3 different rates** (temp-chassis 100 ms, imu-accel 10 ms, batt-voltage 500 ms) | `glaned: 6 mesures publiées pour 'temp-chassis'`, `60 … pour 'imu-accel'`, `2 … pour 'batt-voltage'` |
| Published objects exist as real files in the guest namespace | `ls -l /dev/shmem` → `temp-chassis.value`, `.quality`, `.seq`, `.ts_ns`, `.unit`, `.info` (same for the two other sensors) |
| Timestamped measurements | `tail -n 5 /dev/shmem/imu-accel.info` → `{"s":"imu-accel","id":2,"seq":56,"ts_ns":550000000,"v_m":5750,"unit":"g","quality":"ok"}` |
| **Latency measured on the target** | `glane-latence: 68 publications, p50=439435 ns, p99=2994900 ns, p99.9=2994900 ns, max=2994900 ns` — each publish call bracketed by two `ClockTime(CLOCK_MONOTONIC)` reads inside the guest |
| **Deterministic replay, measured on the target** | the same description is published twice inside the guest; the capture script extracts both blocks (`REJEU-RUN1` / `REJEU-RUN2`) and compares them byte for byte: `rejeu : IDENTIQUES octet pour octet (6 mesures comparées, rejouées DANS QNX 8.0)` |
| A **QNX resource manager** exposing the sensor | `ATTACH OK /dev/sensors/temp-chassis (depuis /dev/shmem/temp-chassis.value)`, then `/dev/sensors/temp-chassis (pid 77827)` |
| The published value is readable by any client | `cat /dev/sensors/temp-chassis -> 61944` |
| A subscriber reacting to the published data | `gwatch[/dev/shmem/imu-accel.value] value=6750  ALARME (seuil=3000)` |
| **The publisher is restarted after being killed** | `slay glaned` → `gsuper: '/proc/boot/glaned' terminé (reprise #1)` → the publisher republishes (`glane-publish: racine publiee = …`) and appears again in `pidin -F "%n"`. The supervisor takes an explicit restart bound (`gsuper -m N`), so a supervised program that exits on its own can no longer be restarted in an endless loop |
| A real QNX shell | the startup script ends on the interactive `ksh` banner of the guest. Note: in the *proof* capture the `exec ksh -l` step of the startup script reports `Unable to start "exec" (2)`; the interactive shell is provided by the vitrine image (`qnx/glane-vitrine.build` + `qnx/invite.sh`) on the VGA console — see `qnx/VITRINE.md` |

On this guest the publication root falls back to the flat layout
(`glane-publish: racine publiee = /dev/shmem (plat)`): `publish/qnx/glane_publish.c`
publishes `<root>/<name>/<leaf>` and falls back to `<root>/<name>.<leaf>` when the
per-sensor directory cannot be created on the target filesystem. The tree layout
is the contractual one (`CONTRACT.md` §6).

Two prefix strings in the capture (`gsengsensor_resmgr:` / `sor_resmgr:`) are
garbled characters in the recorded console; the program prints `gsensor_resmgr:`
(`target/gsensor_resmgr.c`, lines 120 and 152).

### What is *not* claimed

- No Raspberry Pi 5, no I2C/SPI/GPIO sensor, no hardware of any kind: the
  measurements are synthetic.
- The publication root is the guest's tmpfs, not a PPS node: `glane_publish.c`
  is a file-based publication layer with a documented resmgr path
  (`target/gsensor_resmgr.c`), not a full PPS publisher.
- The supervisor is a small dedicated program (`target/gsuper.c`), not the QNX
  HAM itself: HAM is not part of the installed SDP.
- The published tree is not validated by `gschema` **on the target** (there is
  no Python in the guest): the validator is exercised on the host, on a tree
  built to the contractual layout (see `docs/VIDEO.md` §2).
